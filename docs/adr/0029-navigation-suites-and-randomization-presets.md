# ADR-0029: MuJoCo flight suites and domain-randomization presets

**Status:** Accepted, 2026-10-16. **Implementation:** Native MJCF families and
three Hydra presets; evaluation and release checks remain separately measured.

## Navigation scene decisions

Preserve the eight original S/D cases. Add independently designed MuJoCo-native
Forest, Maze, Dense Obstacles, and Dynamic Dense Obstacles cases, each at Easy,
Medium, and Hard difficulty. These cases use physical obstacle geometry, fixed
start/goal semantics, and the existing task/collision/sensor code. Each file is
a reproducible MJCF asset generated by `tools/build_navigation_scenes.py`.
The dynamic cases use the project's existing MuJoCo mocap `body.user` motion
contract. The generator uses deterministic seeds; Benchmark always loads the
baked assets and never regenerates a different world at evaluation time.

FlightBench provides the task-family and increasing-difficulty inspiration:
<https://github.com/thu-uav/FlightBench>. These assets are **independent geometry
reproductions of those task types** rather than the original FlightBench world
files or exact numeric results. Their metrics use the existing FlightBench-like
flight quality and AvoidBench-like path-efficiency protocols.

The initial fixed suite (`S01`, `S02`, `S03`, `S06`, `D01`, `D02`, `D03`, `D06`)
remains the default Benchmark for reproducibility. New scene names are selectable
by Hydra, and the Command Builder exposes optional extended scene families.
The original 230-command core matrix retains its historical execution evidence;
the expanded 486-command matrix requires separate execution acceptance.

## Domain-randomization decisions

Use one Hydra group, `randomization={nominal,dynamics,sim2real}`, rather than
adding an Isaac Lab-style Manager hierarchy. The existing Crazyflow reset and
step pipelines perform the actual sampling and force application.

| Preset | Dynamics parameters | Timing and disturbance |
|---|---|---|
| `nominal` | Nominal parameters | Nominal delays; no added force |
| `dynamics` | Per-world mass, inertia, motor-strength, drag ranges | No additional delay or gust |
| `sim2real` | Broader ranges for those parameters | Random actuation delay, measurement latency, bounded gust force |

These ranges are experimental hypotheses, not hardware-calibrated confidence
intervals. The present `sim2real` preset does **not** include per-pixel depth
noise, per-point LiDAR noise or image appearance randomization. Those features
need a real sensor observation implementation before they can be advertised.
Randomized conditions are training-time variables; formal comparisons fix their
evaluation protocol and never quietly randomize benchmarks.

RotorPy uses a different but compatible organization: `Environment` receives
independent vehicle, controller, trajectory, world, wind and sensor objects;
vehicle dynamics take a physical-parameter dictionary including aerodynamic
coefficients, motor response and noise. RotorPy wind profiles and IMU/mocap
sensor models are independent modules, rather than a Hydra configuration group
or a global manager. See
<https://github.com/spencerfolk/rotorpy/blob/main/rotorpy/environments.py> and
<https://github.com/spencerfolk/rotorpy/blob/main/rotorpy/vehicles/multirotor.py>.
Keep Drone Playground's existing Simulation objects and Crazyflow pipelines;
borrow the explicit parameter ownership and wind/sensor separation rather
than transplanting RotorPy's simulator.

## Play and Benchmark

Keep separate top-level `play` and `benchmark` commands and reuse the same
Simulation rollout implementation. Play is inspection and replay; Benchmark
adds fixed case lists, standardized measurements and batch reports. The two
entrypoints must not create independent physics or action semantics.
